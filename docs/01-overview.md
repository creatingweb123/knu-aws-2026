# 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | 취소된 하루를 양도합니다 (AWS Skill Training 1조) |
| 서비스명 | 이어온 하루 |
| 형태 | 모바일 웹 (React) + 서버리스 API (AWS) |
| 한 줄 요약 | 사정이 생겨 실현하지 못한 일상 계획(취소된 하루)을 다른 사람에게 양도하고, 그 사람이 직접 경험한 기록과 이야기를 돌려받는다 |

## 1.1 문제 정의

> **서비스의 본질.** 이어온 하루는 *실현하지 못한 일상 계획을 다른 사람에게 양도하고, 그 사람이 직접 경험한 결과와 이야기를 원래 계획자에게 돌려주는* 서비스다. 핵심 가치는 계획의 양도, 경험의 공유, 경험의 반환이다. 산책은 대표 활용 사례 중 하나일 뿐이며, 산책 경로·코스를 공유하거나 추천하는 서비스가 아니다. 계획에는 장소 목록이 들어 있지만, 핵심은 장소가 아니라 그 계획을 세운 사연(왜 이 하루를 준비했고, 왜 취소됐는가)과 그 하루를 이어받은 사람이 돌려주는 경험 기록이다.

이 문서는 아래 세 층을 구분해서 쓴다.

| 층 | 내용 | 바뀌는가 |
|---|---|---|
| 서비스의 본질 | 계획·사연 작성 → AI 정리 → 공개 → 실행자 확정 → 실행 → 경험 기록 → 원래 계획자에게 반환 → 답장. 양도와 반환이 중심이다 | 아니오 |
| MVP 적용 범위 | 다른 사람이 대신 경험할 수 있는 짧은 일상 활동. 짧은 시간 안에 끝나고, 공개 장소 중심이며, 장소 1–3곳(계획 저장 기준. AI 초안은 0–3곳), 계획 하나당 실행자 한 명, 기한 3일, 경험 기록은 글 + 선택 사진 1장 | 시범 운영 결과에 따라 넓힐 수 있다 |
| 대표 활용 사례 | 동네 산책, 카페·음식점 방문, 서점·소품점 둘러보기, 전시회·문화공간 관람, 공원에서 쉬기, 특정 장소 사진 촬영, 추억의 장소 다시 가 보기, 여러 곳을 잇는 짧은 나들이 등. 예시일 뿐 고정 목록이나 분류가 아니다 | 예시이므로 제한하지 않는다 |

데모 시나리오(지연, 수현, 민준의 빵집과 하천 벤치 산책)는 위 대표 활용 사례 가운데 하나를 골라 흐름을 보여 주는 것이다. 문서와 화면 문구를 쓸 때는 모든 활동에 공통인 문구와, 이 데모 사례에서만 쓰는 문구를 구분한다.

이사를 앞둔 지연은 5년간 살던 동네에서 마지막 하루를 보내려 했다. 이 대표 사례에서 계획은 동네 산책이었다. 출근길에 지나치던 빵집에 들러 빵을 사고, 저녁마다 걷던 하천 벤치에 앉아 쉴 계획이었다. 이삿짐 정리가 길어져 계획은 휴대폰 메모에만 남았다.

같은 주말 그 동네로 이사 온 수현은 지도에서 주변 가게를 찾았지만 어디서부터 시작할지 정하기 어려웠다. 지연이 하지 못한 하루를 사연과 함께 넘겨받으면, 수현은 그 하루를 대신 보내 볼 계기를 얻는다. 수현이 다녀온 이야기는 지연에게 돌아간다.

같은 구조는 다른 계획에도 성립한다. 일정이 바뀌어 가 보지 못한 동네 서점, 전시 마지막 주에 놓친 전시회, 이사 전에 찍어 두려던 골목 사진, 오래된 단골 카페처럼 한 곳만 가는 계획도 있고, 걷지 않고 앉아서 보내는 활동도 있다. 어느 경우에도 흐름은 같다. 계획자는 계획과 사연을 넘기고, 실행자는 직접 겪은 일을 기록으로 돌려준다.

지연과 수현은 서비스 흐름을 설명하는 가상 인물이며, 데모 계정 이름으로도 쓴다.

## 1.2 사용자

| 역할 | 설명 | 데모 계정 |
|---|---|---|
| 계획자 | 이사, 일정 변경, 컨디션 등 사정으로 계획했던 일상 활동을 하지 못한 사람 | 지연 |
| 실행자 | 남이 남긴 하루를 이어받아 직접 경험해 보고 싶은 사람. 데모에서는 새로 이사 와서 동네를 알아 가려는 사람 | 수현, 민준(인수 경합 시연용) |

동네 문화공간은 초기 도입 후보다. 취소된 하루를 모집하고 참여·완료 현황을 확인하는 프로그램으로 운영할 수 있는지 검토하며, 운영 부담, 다음 회차 운영 의사, 운영비 지불 의사는 시범 운영에서 확인한다. 운영자용 기능은 MVP에 넣지 않는다.

## 1.3 핵심 흐름

```
[지연] 사연 입력 → AI와 함께 정리(질문에 답하기)·수정 → 하루 공개
[수현] 둘러보기 → 하루 들여다보기 → 이어받기 → (그 하루를 보냄) → 경험 기록 작성(+사진) → 전송
[지연] 수신함 알림 → 돌아온 하루 읽기 → 한 줄 답장
```

## 1.4 목표

초안에서 정한 목표는 네 가지다.

1. **서비스 구현**: 취소된 하루를 한 사람이 이어받아 직접 경험하고, 그 경험 기록이 원래 계획자의 수신함에 도착하는 웹서비스를 만든다. MVP는 다른 사람이 대신 경험할 수 있는 짧은 일상 활동만 다룬다(공개 장소 중심, 장소 1–3곳). 한 동네로 운영 범위를 고정하는 것은 시범 운영을 위한 정책이며, 서비스가 동네 산책이어야 한다는 뜻이 아니다.
2. **AI 정리 효과 측정**: 사연을 AI가 활동 목록, 계획 이유, 방문 질문 한 개로 정리한다. 직접 작성할 때와 AI 초안을 편집할 때의 소요 시간, 원문에 없던 장소·활동이 추가된 건수를 비교한다. 다양한 일상 활동의 사연에서도 같은 정리 규칙이 통하는지 본다([§7.5](./07-development-plan.md)).
3. **시범 운영 목표**: 이어받기가 확정된 최초 5건 중 3건 이상이 기한 안에 경험 기록을 보내고, 완료 건 중 2건 이상에서 계획자가 답장을 남긴다.
4. **정합성**: 여러 사용자가 동시에 같은 계획을 요청해도 한 명만 확정한다. 같은 완료 요청을 재시도해도 경험 기록과 수신함 알림은 한 건씩만 남는다.

2번의 "AI 정리"는 초안에서는 단발 호출이었으나, 이후 세션형 정리 에이전트로 바뀌었다. 배경과 설계는 [4. AI 에이전트](./04-ai-agent.md)에 있다.

## 1.5 백엔드가 보장하는 것

초안 목표에서 도출한 여덟 가지 보장이다. 이후 문서에서 G1–G8로 부른다.

| # | 요구 | 구현 수단 |
|---|---|---|
| G1 | 동시에 같은 계획을 요청해도 **한 명만 확정** | DynamoDB 조건부 갱신(TransactWriteItems) |
| G2 | 같은 완료 요청을 재시도해도 **경험 기록·수신함 알림은 한 건** | 결정적 키(`claimId`) + `attribute_not_exists` 조건 + 멱등 응답 |
| G3 | 실행자가 포기한 뒤 들어온 **이전 요청은 거부** | 모든 쓰기에 `plan.currentClaimId = :claimId` 조건 |
| G4 | 완료 상태·경험 기록·수신함 항목은 **하나의 트랜잭션** | TransactWriteItems |
| G5 | 계획별 작성자·실행자 **권한 검사** | Cognito JWT의 `sub`를 Lambda에서 비교 |
| G6 | AI 카드는 에이전트가 검사·수정한 뒤 반환하고, **사용자가 확인한 카드만 저장** | 에이전트 그래프(LangGraph) + 서버 게이트, 저장은 `POST /plans`에서만 |
| G7 | 사진은 비동기 처리, **위치 메타데이터 제거**, 실패 시 글로 완료 가능 | S3 → SQS → Lambda, DLQ |
| G8 | 오류·처리 시간 추적, 새 스택 배포 후 검증 | CloudWatch, AWS SAM |

프로젝트의 핵심 검증 대상은 G1–G4다. 개발 일정이 밀릴 때도 이 부분의 통합 테스트(T3–T7)를 먼저 통과시킨다.

## 1.6 MVP 범위

프론트엔드와 백엔드의 범위를 기능별로 나란히 놓았다. MVP가 받는 계획은 다른 사람이 대신 경험할 수 있는 짧은 일상 활동이다(세 층의 구분은 §1.1). 장소 수와 기한 같은 제약은 시범 운영을 검증하기 위한 범위이고, 서비스의 정의가 아니다.

### 포함 (P0)

| 기능 | 프론트엔드 | 백엔드 |
|---|---|---|
| 인증 | 로그인·회원가입(닉네임 필수) | Cognito User Pool, PreSignUp Lambda로 자동 확인(인증 코드 단계 없음) |
| 둘러보기 | 이어받기 가능한 하루 목록 | 계획 목록·상세 조회 |
| 하루 들여다보기 | 계획 상세, 이어받기, 경합 실패 안내 | 이어받기 확정(G1), 포기, 기한 관리 |
| 하루 남기기 | 사연 입력 → AI 정리(질문 최대 2개, 건너뛰기 가능) → 편집 → 공개. AI 실패 시 직접 작성 | AI 하루 카드 정리 에이전트(세션형, 레벨 0 포함), 사용자당 하루 10세션 제한, 계획 생성(멱등 키) |
| 내 하루 | 이어받은 하루와 기한, 이어받기 포기 | `GET /me/claims` |
| 경험 기록 | 글 + 선택 사진 1장, 사진 처리 대기·실패·교체, 글로 완료 | 기록 저장, 업로드 URL 발급, 사진 비동기 처리, 완료 트랜잭션(G2–G4) |
| 수신함 | 새 편지·읽은 기록 구분, 미확인 표시 | 목록·상세·읽음 |
| 돌아온 하루 | 계획과 경험 기록 나란히 보기, 한 줄 답장 | 답장(1회) |
| 측정 | 작성 소요 시간 전송 | 작성 시간, AI 충실도·질문·개인정보 지표, 기한 내 완료, 답장 여부 저장 |
| 배포·검증 | CloudFront 배포 URL에서 동작 | SAM 단일 스택, 알람, 검증 시나리오 T1–T22 |
| 로컬 개발 환경 | MSW 목업, 로컬 백엔드 연동 모드 | docker compose(AWS 호환 에뮬레이터, HTTP 어댑터, Fake LLM). 개발과 단위·로컬 통합 테스트용 |

### 이후 (P1)

- 실행자가 계획자의 답장 확인 (`GET /me/claims` 응답에 `reply` 포함)
- 실행자 질문 도우미 (조건부): 경험 기록 작성 시 다음에 무엇을 물을지만 에이전트가 고른다. 편지는 실행자 답변을 고치지 않고 순서대로 이어 붙인 초안으로만 준다.
  - 시작 조건: 하루 카드 에이전트(6b단계)가 T18–T22를 통과하고, 3·4단계가 끝나 있어야 한다. 일정이 밀리면 가장 먼저 뺀다.
  - 도구 4개: `get_visit_context`(읽기), `check_coverage`(결정적), `ask_executor`(세션 쓰기, 턴 종료), `finish`. PK는 `HELPER#{claimId}`로 분리한다(IAM LeadingKeys 적용).
  - `Record.composeMode`는 `PUT /record`의 선택 필드로만 받는다. 완료 트랜잭션과 InboxItem은 바꾸지 않는다. 라벨은 `GET /inbox/{itemId}`가 Record에서 읽는다. 90초 시연에는 넣지 않는다.
- 계획 대표 사진 (같은 사진 파이프라인 재사용) — 이번 일정에서 하지 않음
- `GET /me/plans` — 이번 일정에서 하지 않음

### 제외

- 지도, 경로 탐색, 경로 지도, 산책 경로·코스 추천·공유 (이 서비스는 취소된 하루의 양도와 경험 반환이 목적이다)
- 결제, 예약, 실시간 위치 공유·추적
- 다중 실행자(계획 하나당 실행자는 한 명), 며칠에 걸친 장기 여행
- 위치 기반 탐색, 여러 동네 선택. 한 동네만 받는 것은 MVP 운영 범위 정책이다. 서비스가 동네 산책이어야 한다는 뜻이 아니며, 확장에 대비해 `areaId` 필드만 예약한다
- 활동 종류별 카테고리 필드·테이블·API (대표 활용 사례는 예시이지 분류가 아니다)
- 푸시·이메일 알림 (수신함과 헤더 배지만 제공)
- 문화공간 운영자 기능, 신고·모더레이션
- 다중 사진, 채팅, 소셜 로그인

## 1.7 데모와 결과물

90초 시연 순서는 다음과 같다. 데모 계정 세 개(지연, 수현, 민준)를 쓴다.

90초 시연은 대표 사례(동네 산책) 하나로 전체 흐름을 보여 준다.

1. 지연이 사연을 입력하고 AI와 함께 정리한다(질문 1개에 답함). 폼에서 다듬고 공개한다.
2. 수현과 민준이 같은 하루를 동시에 이어받는다. 한 명만 확정되고 다른 쪽은 "이미 다른 사람이 이어받았어요" 화면을 본다.
3. 수현이 경험 기록과 사진을 보낸다.
4. 지연이 수신함에서 돌아온 하루를 읽고 답장한다.

실행 결과로 남길 자료는 AI 카드 작성 시간과 원문 충실도, 동시 인수·중복 완료 테스트 결과(T3·T5 로그), 오프라인 평가 결과표, SAM 배포 기록이다. 데모 링크는 배포 후 [README](../README.md)에 적는다.

완료 기준 전체는 [§7.7](./07-development-plan.md)에 있다.
