# 5. 화면 명세

화면 목록, 화면별 동작과 분기, 화면 문구 규칙, 디자인 가이드, 화면 시안을 다룬다. 화면은 '실현하지 못한 일상 계획의 양도와 경험의 반환'을 다루며 산책 전용이 아니다. 산책(지연·수현·민준의 빵집과 하천 벤치)은 시안과 데모의 대표 사례다. 공통으로 쓰는 문구와 이 사례에서만 쓰는 문구의 구분은 [§5.2.7](#527-화면-문구-규칙)에 있다. API 형식은 [§3](./03-api-contract.md), 요구사항 ID는 [§6.5](./06-requirements.md)에 있다.

## 5.1 화면 목록

하단 탭: **둘러보기 / 내 하루 / 수신함**. 상단 헤더 오른쪽 편지 아이콘에 미확인 수신함 점 표시.

| # | 화면 | 경로 (예시) | 시안 | 주요 동작 |
|---|---|---|---|---|
| 0 | 로그인 / 회원가입 | `/login` | 없음 | 이메일·비밀번호·닉네임. 백엔드가 가입 즉시 자동 확인하므로 인증 코드 단계 없음 |
| 1 | 둘러보기 | `/` | 있음 | 이어받기 가능한 하루 카드 목록(제목, `summary`, 소요 시간, 장소 수), "취소된 하루 남기기" 버튼 |
| 2 | 하루 들여다보기 | `/plans/:planId` | 있음 | 계획자 이름·취소한 이유(`reason`), 방문할 장소(장소·하고 싶었던 일·고른 이유), "이 하루 이어받기" |
| 2-1 | 이미 이어받은 하루 | 같은 경로, 상태 분기 | 있음 | 409 `ALREADY_CLAIMED`, 또는 `status === 'CLAIMED'`이고 내 것이 아닐 때 안내 + "다른 하루 둘러보기" |

| 3-1 | AI와 함께 정리하기 | `/plans/new/card` | **없음** | 단계 칩, 질문 말풍선(선택지·직접 입력·건너뛰기), "이대로 카드 받기", 카드 미리보기, "AI가 바꾼 것" 메모(출처 칩, 다시 넣기), "폼에서 다듬기" |
| 3-2 | 하루 남기기 (폼) | `/plans/new/form` | 있음 | 제목, 하고 싶었던 일 요약, 취소한 이유, 예상 소요 시간, 방문할 장소(1~3곳), 방문 질문 |
| 3-3 | 장소 추가 | `/plans/new/place` | 있음 | 장소 이름, 하고 싶었던 일, 이 장소를 고른 이유 |
| 3-4 | 공개 완료 | `/plans/:planId/published` | 있음 | "둘러보기로 가기" |
| 4 | 내 하루 (이어받음) | `/me` | 있음 | 기한("11월 21일까지…"), 방문할 장소, "다녀온 이야기 쓰기", "이어받기 포기", 맨 아래 계정 영역(닉네임, "로그아웃") |
| 4-1 | 이어받기 포기 확인 | `/claims/:claimId/abandon` | 있음 | "계속 이어가기" / "이어받기 포기" |
| 4-2 | 로그아웃 확인 | 4 위의 확인 시트(경로 없음) | 없음 | "계속 쓰기" / "로그아웃", 보내지 않은 글 경고. 로그아웃하면 0으로 |
| 5 | 그날의 이야기 (경험 기록 작성) | `/claims/:claimId/record` | 있음 | "{계획자}에게" 편지, 하루 카드의 방문 질문 표시, 사진 1장 선택(선택 사항) |
| 5-1 | 보내는 중 (사진 처리 중) | `/claims/:claimId/sending` | 있음 | 진행 표시, 상태 폴링, "글로 완료하기" |
| 5-2 | 사진 처리 실패 | 같은 경로, 상태 분기 | 있음 | "사진 바꾸기" / "글로 완료하기", 작성한 글 유지 |
| 5-3 | 사진 교체 | `/claims/:claimId/record/photo` | 있음 | 새 사진 첨부, "글로 완료하기" |
| 5-4 | 전송 완료 | `/claims/:claimId/done` | 있음 | 사진+글 / 글만 두 가지 문구, "둘러보기로 돌아가기" |
| 6 | 수신함 | `/inbox` | 있음 | 새 편지 / 읽은 기록 배지, 사진 유무에 따라 문구 다름 |
| 7 | 돌아온 하루 | `/inbox/:itemId` | 있음 | 사진, "내가 남긴 계획" vs "{실행자}의 경험 기록", 한 줄 답장 입력 |
| 7-1 | 답장 보낸 상태 | 같은 경로, 상태 분기 | 있음 | "보낸 답장" 읽기 전용, "수신함으로" |
| 8 | 종료된 이어받기 안내 | 상태 분기 | 없음 | 포기·기한 만료로 이어받기가 끝났을 때. 작성한 글 복사 가능, "다른 하루 둘러보기" |

시안이 없는 화면(0, 3, 3-1, 8)은 기존 시안의 톤(큰 제목 + 보조 문구 + 하단 고정 주 버튼)을 따라 만든다.

공통 인증 처리: 401(`UNAUTHORIZED`)을 받으면 현재 경로를 `/login?redirect=...`로 넘기고, 로그인 후 그 경로로 돌아온다.

## 5.2 화면별 상세 요구사항

### 5.2.1 둘러보기
- `GET /plans?status=OPEN` 결과를 최신순 카드로 표시. 빈 목록이면 "아직 남겨진 하루가 없어요" + 하루 남기기 유도.
- 카드: 상태 배지(이어받기 가능), 제목, `summary` 2줄 말줄임, `약 {n}분 · 장소 {k}곳`. (기한이 지난 이어받기는 서버가 `OPEN`으로 내려준다.)
- 내가 남긴 하루도 목록에 보일 수 있다. 이어받기 가능 여부는 상세의 `claimable`로 판단한다.

### 5.2.2 하루 들여다보기 / 이어받기
상세 화면 분기 (위에서부터 먼저 맞는 것 하나):
1. 404 `NOT_FOUND` → "이 하루는 더 이상 볼 수 없어요" + 둘러보기
2. `myClaim?.status === 'ACTIVE'` → "내가 이어받은 하루" 배지 + "내 하루로 가기" 버튼
3. `isOwner` → "내가 남긴 하루" 배지, 상태(공개/이어받음/완료)만 표시, 버튼 없음
4. `claimable` → "이 하루 이어받기" 버튼
5. `status === 'CLAIMED'` → 2-1 안내
6. `status === 'COMPLETED'` → 완료 배지, 읽기 전용
7. 그 외 → 방문할 장소만 보여주고 "다른 하루 둘러보기" 버튼 (방어용)

`myClaim`은 진행 중(`ACTIVE`)이거나 완료(`COMPLETED`)한 내 이어받기만 담긴다. 포기했던 하루는 다시 `claimable`이 될 수 있다.

이어받기 클릭 → `POST /plans/{planId}/claims`
- 201 또는 200(같은 사용자의 중복 요청 — 기존 이어받기 반환): 내 하루(`/me`)로 이동.
- 409 `ALREADY_CLAIMED`: 2-1 상태로 전환 (페이지 이동 없이 같은 화면에서 안내 박스 표시).
- 409 `CANNOT_CLAIM_OWN_PLAN`: 버튼 비노출이 정상이지만 방어적으로 토스트 처리.
- 버튼은 요청 중 비활성화.

### 5.2.3 하루 남기기 (AI와 함께 정리하기 포함)
흐름: **사연 입력 → (AI 정리: 질문에 답하기) → 카드 확인 → 폼 편집 → 공개**

- 사연 입력(최대 1,000자). 입력 예시(placeholder)는 산책 한 가지가 아니라 일상 활동의 폭을 보여 준다([§5.2.7](#527-화면-문구-규칙)). 공개 장소만 적도록 안내 문구 표시 ("집 주소나 개인 정보는 적지 말아주세요").
- 사연 입력 화면에 외부 AI 전송 안내를 둔다. 예: "AI와 함께 정리하기를 누르면 사연이 외부 AI 서비스(<공급자명>, <처리 국가>)로 전송되고, 공급자 정책에 따라 최대 N일 보관될 수 있어요." 공급자에 따라 국외 전송·보존 정책이 다르므로 `<공급자명>`·`<처리 국가>`·`N`은 백엔드가 공급자를 정한 뒤(백엔드 `LLM_PROVIDER_LABEL`과 같은 값) 채운다(문구·위치는 FE-Q6).
- "직접 작성하기"는 AI 호출 없이 폼으로 이동. `summary` 기본값으로 사연 앞부분을 채운다.

**AI와 함께 정리하기 (화면 3-1, 세션 상태 머신)**

"AI와 함께 정리하기" → `POST /ai/card-sessions { story }` → `SessionView`. HTTP 요청 1번이 에이전트 1턴이다. 이후 모든 응답의 `status`로만 분기하고, 응답의 `turn`을 다음 요청의 `expectedTurn`으로 그대로 쓴다.

```
POST /ai/card-sessions ─▶ WORKING ──(자동) turns { expectedTurn } ─────────────────▶ 다시 분기
                          │         연속 2회 WORKING이면 turns { expectedTurn, finish: true }
                          ├ ASKING ── 답하기 / 건너뛰기 / "이대로 카드 받기" ─▶ turns ─▶ 다시 분기
                          ├ READY ─── 카드 미리보기 + 메모 ─▶ "폼에서 다듬기" ─▶ 폼(3-2)
                          └ FAILED(503 AI_UNAVAILABLE) ─▶ 사연 유지, 직접 작성 폼
```

- 생성 응답이 바로 `READY`일 수 있다(레벨 0, `AGENT_MODE=pipeline`). 화면은 어떤 응답에서든 네 상태를 모두 처리한다. 레벨 0에서는 질문 말풍선만 나오지 않는다.
- **단계 칩**: `trace[]` 항목 하나를 칩 하나로, `summary`를 칩 문구로 써서 `step` 순서대로 켠다([§3.2](./03-api-contract.md) 예시 기준: "'골목 빵집' 원문에 없음, 소요 시간 정보 없음 → '출근길 빵집'으로 고침, 개인정보 확인 통과 → 소요 시간 질문"). 응답마다 새로 붙은 단계만 이어서 켠다. 스트리밍은 없다. MSW `ai-ask`도 이 예시를 따른다.
- **WORKING**: 단계 칩을 보여 주며 `answer` 없이 `turns { expectedTurn }`를 자동으로 보낸다. `WORKING`을 연속 2회 받으면 다음 요청에 `finish: true`를 넣고, 그 뒤 `WORKING`이 와도 `finish: true`로 이어서 보낸다(서버가 finish를 세션에 기록하고 모델 호출 예산 안에서 `READY`로 끝낸다). 연속 횟수는 다른 상태를 받으면 0으로 되돌린다.
- **ASKING**: 질문 말풍선을 띄운다. 요청 중에는 말풍선의 답변·건너뛰기 버튼을 비활성화한다.
  - `question.text`, 보조 문구로 `question.reason`.
  - `options[]`를 선택지 버튼으로 → `answer: { questionId, choice }`.
  - `allowFreeText === true`일 때만 직접 입력칸(1–100자) → `answer: { questionId, text }`.
  - "건너뛰기" → `answer: { questionId, skipped: true }`. 건너뛴 필드는 폼에서 `MISSING`으로 남는다.
  - "이대로 카드 받기" → `turns { expectedTurn, finish: true }`. `answer` 없이 보내면 현재 질문은 건너뛴 것으로 처리된다. 이 버튼은 WORKING 중에도 보이고 요청 중에도 누를 수 있다. 요청 중에 누르면 다음 요청에 `finish: true`를 예약만 한다(중복 예약 방지).
  - 예(데모 사례): "빵집과 하천 벤치까지, 산책은 대략 얼마나 걸릴 예정이었나요?" [30분] [45분] [1시간]. 질문은 사연에 맞게 만들어지므로 산책이 아닌 계획에서는 "전시는 대략 얼마나 걸릴 예정이었나요?"처럼 그 활동 이름을 쓴다. 비공개 장소 질문은 모든 활동에서 "[장소에서 빼기] [직접 바꾸기(입력)]" 형태로 온다.
- **READY**: 카드 미리보기와 "AI가 바꾼 것" 메모를 보여 주고 "폼에서 다듬기"로 폼(3-2)에 간다. 모드는 `AI_EDITED`.
  - `card`의 필드 이름이 `POST /plans` 요청과 같으므로(`title`, `summary`, `reason`, `estimatedMinutes`, `places[].name/activity/whyChosen`, `question`) 그대로 폼 초기값으로 쓴다. `null`인 값은 빈칸.
  - `flags`에 `NOT_IN_SOURCE`가 없으면 카드 미리보기에 "원문 대조 통과" 배지를 붙인다. "0건 보장" 같은 문구는 쓰지 않는다.
  - `flags[].path`(예: `places[0].name`)를 폼의 같은 경로 입력칸에 연결한다. `NOT_IN_SOURCE` → "원문에 없던 내용이에요, 확인해 주세요", `MISSING` → "직접 채워주세요", `PRIVACY` → "공개하기 어려운 정보일 수 있어요".
  - 메모: `notes[]`마다 `reason`과 출처 칩(`STORY` → "원문", `ANSWER` → "내 답변")을 붙인다. 예: "'골목 빵집' 대신 원문의 '출근길 빵집'으로 적었어요 · 원문".
  - `action === 'REMOVED'` 메모에는 "다시 넣기" 버튼을 둔다. 누르면 그 항목을 폼에 되살리고 `PRIVACY` 또는 `NOT_IN_SOURCE` 경고를 함께 붙인다(복원할 값·유형·위치는 FE-Q7).
  - `degraded === true`여도 같은 화면이다. 남은 `flags`가 폼에 그대로 연결된다.
- **동시 요청·재동기화**
  - 409 `AI_SESSION_BUSY` → 2초 뒤 `GET /ai/card-sessions/{sessionId}`로 다시 맞추고 그 상태로 분기한다.
  - 재동기화 `GET`이 보낸 `expectedTurn`과 같은 `turn`의 `WORKING`이면 다른 요청이 아직 처리 중이다(서버는 잠금을 잡을 때 `WORKING`으로 바꾼다). 2초 간격으로 `GET`을 반복하고, 이 응답은 연속 `WORKING` 횟수에 넣지 않는다. 잠금 시간(30초)이 지나도 같으면 `turns { expectedTurn }`를 다시 보낸다.
  - 409 `AI_SESSION_CLOSED` → `GET`으로 현재 상태(`READY`·`FAILED`)를 받아 보여 준다.
  - 보낸 `expectedTurn`이 이미 지난 턴이면 서버가 모델을 부르지 않고 현재 `SessionView`를 200으로 돌려준다. 프론트는 받은 응답으로 그대로 분기한다.
- **새로고침 복구**: 3-1에 들어올 때 작성 중 상태에 `sessionId`가 있고 `READY` 카드가 없으면 `GET /ai/card-sessions/{sessionId}`로 상태를 받아 이어간다(`WORKING`이면 자동 요청 재개).
- **실패**(`FAILED`/503 `AI_UNAVAILABLE`, 502 `AI_INVALID_OUTPUT`, 429 `AI_QUOTA_EXCEEDED`, 세션 404 `NOT_FOUND`, 타임아웃, 그 외 5xx): **입력한 사연을 그대로 유지**하고 "AI 카드를 만들지 못했어요. 직접 정리해 주세요" 안내 후 빈 폼(사연은 참고용으로 상단에 표시)으로 이동. 이때 `mode`는 `MANUAL`이고 `aiSessionId`는 보내지 않는다.
- 요청당 응답은 30초 안에 정해진 코드로 온다([§3.2](./03-api-contract.md) 12초 규칙). AI 세션 요청의 클라이언트 타임아웃은 30초보다 길게 잡는다. 로컬 백엔드 모드의 LLM 기본값은 Fake 채팅 모델이다. 백엔드가 네이티브 Ollama를 붙이면 read 타임아웃과 어댑터 실행 시간을 늘리므로 30초 상한이 지켜지지 않을 수 있다. 타임아웃 동작은 `dev` 스택에서 확인한다.
- `turns` 요청이 네트워크 오류·클라이언트 타임아웃으로 끝나면 바로 직접 작성으로 가지 않고 `GET`으로 한 번 재동기화한 뒤 그 상태로 분기한다. `GET`도 실패하면 위 실패 처리를 따른다.

**폼과 공개**
- 폼 검증: 제목 1–40자, 하고 싶었던 일 요약(`summary`) 1–120자, 취소한 이유 1–300자, 예상 소요 시간 10–240분, 장소 1–3곳(이름 1–30자, 하고 싶었던 일 1–60자, 고른 이유 0–120자), 방문 질문 1–80자(필수, 1개).
- 사연(1–1,000자)은 두 방식 모두 필수다. 원문에 없던 장소·활동 건수를 서버가 두 방식 모두에 대해 계산하기 때문이다.
- **작성 중 상태 보관**: 사연, `sessionId`, 마지막 `turn`, READY 카드, `flags`, `notes`, 폼 값, `startedAt`, `idempotencyKey`를 하나의 상태로 묶어 `sessionStorage`에 저장한다(장소 추가 화면 이동·새로고침에도 유지). 공개에 성공하면 삭제.
- **공개**: `POST /plans`, 헤더 `Idempotency-Key`.
  - 키는 "이 하루 공개하기"를 누를 때 요청 본문과 함께 만들어 보관하고, 같은 본문을 재전송할 때만 재사용한다. 폼 내용이 바뀌면 새 UUID를 만든다.
  - 409 `IDEMPOTENCY_CONFLICT`를 받으면 새 키로 한 번 다시 요청한다.
- **작성 시간 측정**: `startedAt`은 사연 입력 화면에 처음 들어올 때 한 번만 기록하고(하위 경로 이동 시 재설정하지 않음), 공개 요청에 `authoring`으로 함께 전송한다. `aiSessionId`는 `AI_EDITED`일 때만 넣는다. 질문 대기·편집 시간 분해(`agentWaitMs`, `answerWaitMs`, `editMs`)는 서버가 세션 기록으로 계산한다.
  ```json
  "authoring": { "mode": "AI_EDITED" | "MANUAL", "durationMs": 183000, "aiSessionId": "ais_...", "story": "사연 원문" }
  ```

### 5.2.4 내 하루 / 이어받기 포기
- `GET /me/claims?status=ACTIVE`로 현재 이어받은 하루 표시. 없으면 둘러보기 유도.
- 기한 문구: `dueAt` 기준 "{M}월 {D}일까지 다녀온 이야기를 보내주세요." 기한이 지났으면 "기한이 지났어요. 다른 사람이 이어받기 전까지는 보낼 수 있어요."
- 카드 맨 위 기한 띠에 기한 문구와 **남은 날 칩**을 둔다. 칩은 KST 날짜 차이로 "D-{n}", 기한 당일 "D-day", 지났으면 "기한 지남"(띠도 베이지로 바뀐다).
- **진행 단계 막대**: "이어받음 → 다녀오기 → 경험 기록 보내기" 3칸. 서버에 저장된 기록이 없으면 '다녀오기', 기록이 있거나 사진 처리 중·실패면 '경험 기록 보내기'를 현재 단계로 표시한다(`record` 기준. 실제로 다녀왔는지는 알 수 없으므로 '다녀오기'는 기록 전 단계를 뜻한다).
- 4-1 포기 확인은 완료/확인 화면 패턴(확인 아이콘)에 포기할 하루 요약(제목, 남은 날 칩, 계획자·소요 시간)을 둔다.
- "다녀온 이야기 쓰기" 버튼은 응답의 `record.photoStatus`에 따라 이동한다: 기록 없음/`NONE` → 작성 화면, `UPLOAD_PENDING`/`PROCESSING` → 보내는 중, `FAILED` → 사진 처리 실패.
- 포기: 확인 화면 → `POST /claims/{claimId}/abandon` → 둘러보기로 이동. 409 `CLAIM_NOT_ACTIVE`는 "이미 종료된 이어받기예요" 안내 후 새로고침.

**로그아웃 (FE-AUTH-04)**
- 위치: 내 하루(4) 맨 아래 계정 영역. 지금 로그인한 닉네임(없으면 "닉네임 없음")과 "이 이름으로 로그인했어요", "로그아웃" 버튼. 로그아웃은 드물게 쓰므로 헤더나 새 탭에 두지 않는다.
- "로그아웃" → 확인 시트(4-2). 제목 "로그아웃할까요?", 안내 "이어받은 하루와 남긴 하루는 그대로 있어요. 다시 로그인하면 이어서 볼 수 있어요." 주 버튼은 안전한 쪽 "계속 쓰기", 보조 버튼 "로그아웃"(`danger`). Esc·바깥 누르기·"계속 쓰기"로 닫히고, 열리면 "계속 쓰기"에 포커스가 간다.
- 이 기기에 보내지 않은 글(사연이 있는 하루 남기기 작성 상태, 경험 기록 임시 글)이 있으면 경고 "이 기기에 보내지 않은 글이 있어요 / 로그아웃하면 작성 중인 하루와 경험 기록 임시 글이 지워져요."를 더한다.
- 확인하면: 인증 방식의 로그아웃(Cognito는 이 기기의 토큰만 지운다, dev JWT는 메모리 토큰 삭제) → 이 기기의 작성 중 상태(하루 남기기 작성 상태, 경험 기록 임시 글, 보내는 중 기준 시각)와 조회 캐시 삭제 → 로그인 화면(0)으로 이동, redirect는 붙이지 않는다 → 토스트 "로그아웃했어요". 공용 기기에서 다음 사람이 앞사람의 글을 보지 않게 하려는 것이다. 서버의 이어받기·계획·수신함은 그대로다.
- 로그아웃 요청이 실패하면 토스트 "로그아웃하지 못했어요. 다시 시도해 주세요."를 띄우고 화면과 글을 그대로 둔다.
- 목업 모드에는 계정 영역을 그리지 않는다(목업 바가 사용자를 바꾼다).

### 5.2.5 경험 기록 작성 / 사진 / 완료
상태 흐름 (서버의 `record.photoStatus` 기준):

```
글 작성 ─┬─ 사진 없음 ─ PUT /record { letter } ─▶ POST /complete (TEXT_ONLY) ─▶ 전송 완료
         └─ 사진 선택 ─ PUT /record { letter, photo } ─▶ upload.url로 S3 PUT
                             └▶ 보내는 중 (폴링 GET /record, 2초 간격)
                                 ├ delivered ─────────▶ 전송 완료
                                 ├ FAILED ────────────▶ 실패 화면: 사진 바꾸기 / 글로 완료
                                 └ (언제든) "글로 완료하기" ─▶ PUT /record { letter } ─▶ POST /complete (TEXT_ONLY)
```

- **"글로 완료"는 항상 `PUT /record`로 현재 글을 먼저 저장한 뒤 `complete`를 호출한다.** 400 `RECORD_REQUIRED`를 받으면 `PUT /record` 후 1회 재시도.
- 작성 화면 상단에 계획 제목, "{계획자 닉네임}에게" 라벨, 하루 카드의 **방문 질문**을 보여준다.
- 작성 화면 진입 시 `GET /claims/{claimId}/record`로 서버에 저장된 글을 먼저 채우고, 없을 때만 `localStorage` 임시 글을 쓴다. 임시 글은 전송 완료·종료 안내 시 삭제.
- 글 1–1,000자. 사진은 JPEG/PNG, 10MB 이하, 1장. 클라이언트에서 크기·형식 1차 검증.
- `PUT /claims/{claimId}/record` 응답의 `upload`로 `fetch(upload.url, { method: 'PUT', body: file, headers: upload.headers })`. 업로드 실패 시 실패 화면과 동일하게 처리.
- `upload.url`의 호스트·경로는 바꾸지 않는다. 로컬 백엔드 모드에서는 presigned URL이 `http://localhost:4566` 호스트와 경로 방식 주소로 서명되어 오고, host도 서명에 들어간다.
- 사진 교체: `POST /claims/{claimId}/record/photo` → 새 업로드 URL로 다시 업로드 → 보내는 중.
- 폴링 응답(`GET /record`) 판정 순서 — 위에서부터 먼저 맞는 것:
  1. `delivered === true` → 전송 완료 (`photoStatus === 'READY'`면 사진+글 문구, 아니면 글 문구)
  2. `claimStatus`가 `ABANDONED`/`EXPIRED`, 또는 응답이 403/404/409 → 화면 8
  3. `photoStatus === 'FAILED'` → 사진 처리 실패 화면
  4. 그 외 → 계속 폴링. 60초가 지나도 처리 중이면 "글로 완료하기"를 강조 표시. `UPLOAD_PENDING`이 30초 넘게 바뀌지 않으면 업로드 실패로 보고 실패 화면(사진 바꾸기 / 글로 완료)을 보여준다 (새로고침으로 돌아온 경우 포함).
- **종료된 이어받기**: `PUT /record`, `POST /record/photo`, `POST /complete`가 409 `CLAIM_NOT_ACTIVE`를 반환하거나 폴링 판정 2에 걸리면 화면 8("이 이어받기는 종료되었어요")을 띄운다. 작성한 글은 복사할 수 있게 보여준다. (`photoStatus = DISCARDED`는 글로 완료 성공 때도 나오므로 종료 판단에 쓰지 않는다.)
- `POST /claims/{claimId}/complete`는 재시도해도 안전하다(서버 멱등). 네트워크 오류나 503 `TRY_AGAIN`이면 같은 요청을 자동 1회 재시도.
- **전송 완료 화면 문구**("사진과 경험 기록이…" / "경험 기록이…")는 누른 버튼이 아니라 서버 결과로 정한다: `complete` 응답의 `hasPhoto`, 폴링 경로에서는 `photoStatus === 'READY'`. 완료 화면에서 새로고침하면 `GET /record`로 다시 판단한다.

### 5.2.6 수신함 / 돌아온 하루 / 답장
- `GET /inbox` → 최신순. `read === false`면 "새 편지" 배지 + 주황 점, 아니면 "읽은 기록". 사진 유무로 "사진과 경험 기록을 보냈어요" / "경험 기록을 보냈어요".
- 헤더 편지 아이콘 점과 하단 탭 수신함 점은 `GET /me`의 `unreadInboxCount > 0`일 때 표시.
- 목록 항목: 편지 아이콘 칸(안 읽었으면 주황 점) + 계획 제목 + 배지 + 보낸 문구 + 시간. 읽은 기록은 회색 면으로 가라앉힌다.
- 상세 진입 시 `POST /inbox/{itemId}/read` 호출 후 목록/배지 캐시 무효화.
- 상세: 사진(있으면, `record.photoUrl` presigned GET URL — 만료되면 상세를 다시 조회), 사진 아래 `record.photoCaption`, "내가 남긴 계획"(베이지: `plan.summary`) / "{실행자}의 경험 기록"(연녹색: `record.letter`, 본문보다 큰 글자) 2단 카드. 경험 기록 카드가 계획 카드 아래에 살짝 겹쳐 이어진다. 보낸 답장은 보내기 아이콘이 붙은 읽기 전용 카드.
- 한 줄 답장 1–100자 → `POST /inbox/{itemId}/reply`. 성공 또는 409 `REPLY_ALREADY_SENT`면 "보낸 답장" 읽기 전용 상태로 전환.

### 5.2.7 화면 문구 규칙

화면 문구는 두 종류로 나눈다. **공통 문구**는 어떤 활동의 계획이든 그대로 맞아야 한다. **대표 사례 문구**는 데모 시나리오(지연의 마지막 동네 산책)나 예시 데이터에서만 쓰며, 공통 화면의 고정 문구로 쓰지 않는다.

공통 문구 (활동에 상관없이 쓴다)

| 위치 | 문구 |
|---|---|
| 로그인·소개 | "취소된 하루를 이어받고, 그날의 이야기를 돌려줘요." |
| 둘러보기 설명 | "누군가 하지 못한 하루를 이어받아요." |
| 둘러보기 빈 상태 | "하지 못한 하루가 있다면 첫 하루를 남겨 보세요." (기존 "아직 남겨진 하루가 없어요"와 함께 쓴다) |
| 사연 입력 placeholder | 활동 폭을 보이는 예. 예: "이사 전에 가 보려던 동네 서점에 일정이 바뀌어 못 갔어요." |
| 장소 섹션과 버튼 | 섹션 제목 "방문할 장소", 추가 버튼 "장소 추가하기". 경로·동선을 뜻하는 표현은 쓰지 않는다 |
| 이어받기 종료 안내 | "다른 하루를 둘러보고 이어받을 하루를 골라 보세요." |

| 하루 남기기 폼 | 묶음 제목 "이 하루" / "방문할 장소"(옆에 "{k} / 3곳") / "이어받는 사람에게", 장소의 고른 이유 앞 "고른 이유 ·" |
| 장소 추가 | 이름·하고 싶었던 일 placeholder "예: 동네 빵집", "예: 갓 나온 빵 하나 사기", 새 장소 칩 "새 장소" |
| 내 하루 | 남은 날 칩 "D-{n}" / "D-day" / "기한 지남", 진행 단계 "이어받음" / "다녀오기" / "경험 기록 보내기" |
| 사진 선택 | 안내 "JPEG·PNG, 10MB 이하 · 사진의 위치 정보는 지워져요" |
| 계정·로그아웃 | "계정", "이 이름으로 로그인했어요", "로그아웃", "로그아웃할까요?", "계속 쓰기", "로그아웃했어요" (나머지 안내는 §5.2.4) |

| 위치 | 문구 |
|---|---|
| 데모 사연·계획 | 지연의 "이사 전, 마지막 동네 산책", 출근길 빵집, 하천 산책로 벤치, 소요 시간 질문의 "산책은 대략 얼마나" |
| 목업·시드의 예시 | 산책이 아닌 활동(카페, 서점, 전시, 공원 사진 등)을 함께 두어 장소 1곳·걷지 않는 활동도 같은 화면에서 확인한다([§7.5](./07-development-plan.md)) |

규칙

- 일반 문장에 '동선'을 쓰지 않는다. 계획의 장소 목록은 '방문할 장소'다.
- '산책'은 대표 사례 맥락(데모 데이터, 예시 문구, 시안 설명)에서만 쓴다. 고정 UI 문구에서는 '하루'를 쓴다.
- 요구사항 ID, 필드 이름, API 이름(`Record`, `record` 등)은 문구가 바뀌어도 그대로다. 화면에 보이는 말만 '경험 기록'이다.
- 장소 수·소요 시간 표시(`약 {n}분 · 장소 {k}곳`)는 장소 1곳, 소요 시간 없음(`null`)에서도 어색하지 않아야 한다.
- 시안에 없는 새 문구를 정할 때 산책 한 가지를 전제로 쓰지 않는다. 특정 활동에서만 맞는 말이 필요하면 데이터(사연, 카드)에서 가져온다.

## 5.3 디자인 가이드 (시안 기준)

색상은 시안에서 추정한 값이므로 디자인 확정 시 교체한다. 글꼴·크기·간격·모서리·그림자는 2026-11-27 화면 개선안에서 정했다(FE-Q14). 값은 모두 `frontend/src/styles/tokens.css`에 있고, 컴포넌트는 색을 토큰으로만 쓴다.

| 토큰 | 값(추정) | 쓰임 |
|---|---|---|
| `--color-primary` | `#234D3A` | 주 버튼, 제목, 로고, 선택된 탭, "이어받기 가능" 배지, 내 하루 기한 띠 |
| `--color-bg` | `#FAF8F3` | 화면 배경 |
| `--color-surface` | `#FFFFFF` | 카드, 입력칸 |
| `--color-surface-sub` | `#F3F1EB` | 읽은 기록, 남이 이어받은 하루처럼 한 단계 가라앉힌 면, 세그먼트 탭 바탕 |
| `--color-plan` | `#F4ECDD` | "내가 남긴 계획", 계획자 사연 박스, 티켓 위쪽 칸, 확인 아이콘(느낌표) 배경 |

| `--color-danger` | `#A13A28` | 실패 아이콘, 입력 오류, "이어받기 포기" 글자 |

글꼴

- 모든 글자는 `Pretendard`(가변 글꼴, jsDelivr의 동적 서브셋으로 쓰는 글자만 내려받는다). 불러오지 못하면 시스템 한글 글꼴(Apple SD Gothic Neo, Noto Sans KR, 맑은 고딕 순)로 대신한다.
- **실행자가 쓰고 계획자가 읽는 경험 기록 글**(작성 칸, 돌아온 하루 카드, 종료 안내의 작성한 글)은 같은 글꼴에 본문보다 큰 글자(16–17px)와 넓은 줄 간격(1.8)으로 구분한다. 글꼴을 따로 두지 않는다.
- 큰 제목 24px·굵기 800·자간 -0.5px, 본문 15–16px, 보조 문구 12–14px.

레이아웃

- 상단 헤더: 단계 화면은 뒤로가기 + 가운데 제목 + 편지 아이콘. **목록형 화면(하단 탭이 있는 1, 4, 6)은 가운데 제목 대신 왼쪽에 서비스 이름(로고)을 두고**, 화면 이름은 보조 기술에만 읽힌다.
- 본문 좌우 여백 20px. 하단 고정 주 버튼(높이 54px, 모서리 14px, 꽉 찬 폭) 영역은 배경색 + 위쪽 구분선. 버튼 위에 한 줄 안내를 둘 수 있다(예: 2의 이어받기 기한).
- 보조 버튼은 흰 바탕 + primary 테두리. 되돌리기 어려운 동작("이어받기 포기")은 보조 버튼 모양에 빨간 글자(`danger`)로 두고, 안전한 쪽("계속 이어가기")을 주 버튼으로 한다.
- 하단 탭(목록형 화면만): 아이콘 + 이름. 수신함 탭에도 미확인 점을 둔다(FE-COM-02).
- 터치 영역은 44px 이상. 아이콘은 선 아이콘(`components/Icon.tsx`)만 쓰고 이모지는 쓰지 않는다.

패턴

- 큰 제목(2줄, 굵게) + 보조 설명(회색) 패턴을 모든 단계 화면에 공통 적용.
- **하루 카드는 '넘겨받는 티켓' 모양**이다: 위쪽 칸(배지·계획자·장소 번호 원) + 점선 절취선 + 아래 본문(제목·요약·`약 {n}분 · 장소 {k}곳`). 둘러보기 카드, 하루 상세의 위쪽 띠, 3-1 카드 미리보기가 같은 모양이다. 대표 사진 자리를 위쪽 칸이 대신한다(§5.6 4번). 둘러보기 카드의 위쪽 칸은 계획(베이지)과 기록(연녹색) 색을 번갈아 쓴다.
- 방문할 장소는 번호 원 + 세로 연결선 타임라인. 마지막 장소 번호 원은 채운 primary. 번호는 순서를 보이기 위한 것이며 경로나 이동 안내가 아니다(지도·경로 탐색 없음). 장소가 1곳이면 항목 하나만 보이고 그 번호 원이 마지막 장소 규칙을 따른다. 티켓 위쪽 칸의 번호 원은 서로 선으로 잇지 않는다.
- 방문 질문은 연녹색 박스로 같은 모양을 쓴다: 2(이어받기 전에 미리 보기), 3-2(계획자가 쓰는 칸 "이어받는 사람에게"), 5(실행자가 답할 질문).
- 상태 배지: 이어받기 가능(진한 primary) / 이어받음 / 완료 / 공개 / 새 편지(accent) / 읽은 기록 / 내가 남긴 하루 / 내가 이어받은 하루.
- 완료/확인 화면: 원형 아이콘 + 제목 + 설명 + 요약 카드 + 하단 버튼. 아이콘은 색과 모양을 함께 바꿔 뜻을 나눈다(색만으로 구분하지 않음).

| 아이콘 | 모양 | 쓰는 화면 |
|---|---|---|
| 완료 | 숲색 원 + 흰 체크 | 3-4 공개 완료, 5-4 전송 완료 |
| 확인 | 베이지 원 + 느낌표 | 4-1 포기 확인, 2-1 안내, 찾을 수 없음(404) |
| 실패 | 연한 빨강 원 + 느낌표 | 5-2 사진 처리 실패, 불러오기 실패 |
| 종료 | 회색 원 + 시계 | 8 종료된 이어받기 |

화면 개선안 캔버스(2026-11-27): 전 화면 시안을 Claude 디자인 캔버스로 만들었다. 캔버스는 참고용이고 이 절과 구현이 기준이다. 캔버스에는 구현하지 않은 것이 있다: 3-2 소요 시간 빠른 선택 칩, 3-3 필수 칸이 비면 버튼을 끄는 동작, 3-2 공개 버튼 위 경고 개수 안내, 5-1의 보내는 글 요약 카드.

## 5.5 캠퍼스 버전에서 동네 버전으로 바뀐 점

두 PDF를 비교한 결과다. 두 시안 모두 산책 사례를 담은 과거 기록이며 본문은 그대로 둔다. 표의 '동선', '방문 기록', '편지'는 시안 당시 표기이고, 현행 명세는 '방문할 장소', '경험 기록'을 쓴다([§5.2.7](#527-화면-문구-규칙)). 서비스가 산책 전용이라는 뜻이 아니다.

| 항목 | 캠퍼스 버전 | 동네 버전 |
|---|---|---|
| 배경 | 같은 캠퍼스의 선배·후배 | 같은 동네의 계획자·실행자 |
| 예시 인물 | 지민 선배, 서윤 후배 | 지연, 수현 |
| 예시 계획 | 졸업 전, 마지막 캠퍼스 산책 (장소 3곳) | 이사 전, 마지막 동네 산책 (장소 2곳) |
| 둘러보기 버튼 | "내가 보내고 싶었던 하루 남기기" | "취소된 하루 남기기" |
| 계획자 박스 | "지민 선배가 남긴 하루" + 하고 싶었던 일 | "지연 · 취소한 이유" + 취소한 이유 |
| 폼 두 번째 칸 | "남기고 싶은 이유" | "취소한 이유" |
| 장소 입력 | 장소 이름, 하고 싶었던 일 | "이 장소를 고른 이유" 추가. 동선에도 표시 |
| 실행자가 보내는 글 | "편지" | "방문 기록" |
| 작성 화면 버튼 | "사진과 편지 보내기" | "사진과 방문 기록 보내기" + "사진 없이 글로 완료" |
| 보내는 중 | 진행 표시만 | "글로 완료하기" 추가 |
| 사진 실패·교체 | "편지만 보내기" | "글로 완료하기" |
| 이어받기 중단 | "이어받기 취소" | "이어받기 포기". 포기하면 다시 공개된다는 안내 추가 |
| 수신함 | 새 편지 | 새 편지 + 읽은 기록 |
| 답장 후 | 별도 완료 화면("답장을 보냈어요") + 보낸 답장 상태 | 같은 화면에서 "보낸 답장" 읽기 전용으로 전환 |

레이아웃과 색은 두 버전이 같다.

## 5.6 시안과 명세의 차이

시안은 AI 정리 방식을 바꾸기 전에 만들어졌고, 명세가 그 뒤에 더 구체화되었다. 구현할 때 아래 차이를 알고 있어야 한다. 명세와 시안이 다르면 명세를 따르되, 화면 배치는 디자인 담당과 맞춘다.

| # | 차이 | 시안 | 명세 |
|---|---|---|---|
| 1 | 폼(3-2)의 입력칸 | 하루 제목, 취소한 이유, 예상 소요 시간, 방문 동선 | 여기에 하고 싶었던 일 요약(`summary`)과 방문 질문(`question`)이 더 있다. 둘 다 필수다 |
| 2 | 경험 기록 작성(5)의 방문 질문 | 보이지 않는다 | 계획 제목, "{계획자}에게" 라벨과 함께 하루 카드의 방문 질문을 보여 준다 (FE-REC-01) |
| 3 | 예시 장소 이름 | "골목 빵집", "처음 들러 소금빵 사기", "물소리 듣기" | "출근길 빵집", "들러서 빵 사기", "벤치에 앉아 쉬기". 명세에서 "골목 빵집"은 원문에 없는 표현의 예로 쓰인다 |
| 4 | 하루 대표 사진 | 둘러보기 카드와 상세에 커버 사진이 있다 | 이번 일정에서 하지 않는다. 기본 일러스트나 플레이스홀더로 대체 |
| 5 | "편지" 표현 | 사진 교체 화면("작성한 편지는 저장되어 있어요")과 글 전송 완료("편지 전송 완료")에 남아 있다 | 실행자가 보내는 글은 "경험 기록"으로 부른다(시안은 "방문 기록"). 수신함 배지 "새 편지"는 명세에서도 쓴다 |
| 6 | 초안 PDF의 결과 화면 | 데스크톱 형태, "내가 보내고 싶었던 하루 / 누군가 보내고 돌아온 하루", "답장 남기기" | 모바일 2단 카드 "내가 남긴 계획 / {실행자}의 경험 기록", "답장 보내기" |

7부터 12까지는 시안(또는 이전 구현)의 산책 전제 문구가 공통 문구로 바뀐 곳이다. 시안 PDF는 고치지 않는다.

| # | 위치 | 시안·이전 문구 | 현행 문구 |
|---|---|---|---|
| 7 | 장소 섹션 제목, 장소 추가 | "산책 동선", "방문 동선", "동선에 추가하기" | "방문할 장소", "장소 추가하기" |
| 8 | 실행자가 보내는 글 | "방문 기록"(시안), "사진과 방문 기록 보내기" | "경험 기록", "사진과 경험 기록 보내기" |
| 9 | 로그인·소개, 둘러보기 설명 | "취소된 동네 산책을 이어받고…", "누군가 하지 못한 동네 산책을…" | "취소된 하루를 이어받고, 그날의 이야기를 돌려줘요.", "누군가 하지 못한 하루를 이어받아요." |
| 10 | 둘러보기 빈 상태, 종료 안내 | "하지 못한 산책이 있다면…", "이어받을 산책을…" | "하지 못한 하루가 있다면…", "이어받을 하루를…" |
| 11 | 사연 입력 placeholder | 5년 살던 동네를 마지막으로 걷고 싶었다는 산책 예시 | 일상 활동 폭을 보이는 예(동네 서점에 못 간 사연 등) |
| 12 | 비공개 장소 질문 | "동선에서 빼기", "비공개 장소라 동선에서 뺐어요." | "장소에서 빼기", "비공개 장소라 뺐어요." |

3번은 목업 데이터와 seed 데이터를 만들 때 영향을 준다. 시안에는 산책 사례만 있으므로 목업·시드에는 산책이 아닌 활동 예시도 함께 둔다. 프론트엔드 MSW의 AI 경로(`?mock=ai-ask`)는 [§3.2](./03-api-contract.md) 예시("출근길 빵집")를 따르도록 정해져 있다. 예시 계획 데이터를 시안과 명세 중 어느 쪽에 맞출지는 정해지지 않았다.
