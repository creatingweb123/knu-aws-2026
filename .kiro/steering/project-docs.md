# 이어온 하루: 프로젝트 문서 기준

## 기준 문서

- 명세의 기준은 `docs/`다. 문서에 없는 결정을 새로 만들지 않는다. 필요한 결정이 문서에 없으면 `docs/08-open-questions.md`의 해당 질문 번호(`BE-Q*`, `FE-Q*`)와 함께 미결로 표시한다.
- API 계약의 기준은 `docs/03-api-contract.md`다. 요청·응답 형태, 에러 코드, 필드 이름을 임의로 바꾸지 않는다.
- 요구사항 ID(`BE-*`, `FE-*`), 보장(G1–G8), 검증 시나리오(T1–T22), 연동 지점(S0–S5) 번호를 spec과 코드, PR에서 그대로 쓴다.
- `references/`의 초안 PDF, 화면 시안, 권고안은 작성 시점의 기록이다. 현재 설계(LangGraph + LLM 공급자 설정, 로컬 Docker 개발 환경)나 서비스 정의(산책이 아니라 취소된 하루의 양도와 경험 반환)와 다르면 `docs/`를 따른다. 시안의 산책 문구는 대표 사례다.

## 서비스 정체성

- 이어온 하루는 **실현하지 못한 일상 계획(취소된 하루)을 다른 사람에게 양도하고, 그 사람이 직접 경험한 결과와 이야기를 원래 계획자에게 돌려주는 서비스**다. 핵심 가치는 계획의 양도, 경험의 공유, 경험의 반환이다. 산책 경로·코스 공유 서비스가 아니다.
- 문서와 코드, 문구에서 세 가지를 구분한다. (1) 서비스의 본질: 양도와 반환. (2) MVP 적용 범위: 다른 사람이 대신 경험할 수 있는 짧은 일상 활동(공개 장소 중심, 장소 1–3곳, 실행자 한 명, 기한 3일, 경험 기록은 글 + 선택 사진 1장). 한 동네 고정은 운영 범위 정책이다. (3) 대표 활용 사례: 동네 산책, 카페·음식점, 서점·소품점, 전시회, 공원 휴식, 사진 촬영, 추억의 장소, 짧은 나들이 등. 예시일 뿐 고정 목록이 아니다. '동네 산책'(지연·수현·민준)은 데모의 대표 사례 하나다.
- 계획을 '산책 코스'로 한정하거나 경로·동선 공유처럼 읽히게 쓰지 않는다. 화면과 문서에서는 '방문할 장소', 실행자가 쓰는 글은 '경험 기록'(필드·API·요구사항 ID의 `Record`·`REC` 등은 그대로)이라고 쓴다.
- 범위 밖: 지도, 경로 탐색, 결제, 예약, 실시간 위치, 다중 실행자, 장기 여행, 활동 카테고리 필드·테이블·API. 이를 새로 만들려면 먼저 `docs/08-open-questions.md`에 질문으로 올린다.

## 저장소 구조

- 문서와 코드를 한 저장소에 둔다. 백엔드 코드는 `backend/`, 프론트엔드 코드는 `frontend/` 아래에 만든다.
- 문서에 나오는 코드 경로는 영역 폴더 기준이다. 백엔드 경로(`src/...`, `tests/...`, `scripts/seed.py` 등)는 `backend/` 아래, 프론트엔드 경로(`src/api/client.ts` 등)는 `frontend/` 아래다. 루트 `scripts/`는 문서용이다.
- 상세 구조는 `docs/02-architecture.md` §2.10을 따른다.
